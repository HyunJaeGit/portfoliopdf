포트폴리오 코드 검토 및 개선 제안서
작성일: 2026-08-23

1. 검토 목적과 범위

이 문서는 현재 React·TypeScript·Vite 기반 정적 포트폴리오의 전체 소스, 콘텐츠 모델, 스타일, 접근성, 인쇄 기능, 빌드 설정과 GitHub Pages 배포 구성을 검토한 결과를 정리한다. 실제 프로젝트 원본 저장소나 운영 데이터는 이번 검토 범위에 없으므로, 성과·기여 내용의 사실 여부를 새로 단정하지 않고 현재 저장소에서 확인 가능한 표현과 구조만 평가했다.

검토 대상
- src의 페이지, 공통 컴포넌트, 콘텐츠 데이터와 CSS
- Vite·TypeScript·ESLint·패키지 설정
- README, 정적 이미지와 GitHub Actions 배포 워크플로
- 프로덕션 build 및 lint 실행 결과

2. 현재 상태 요약

장점
- Home, Resume, Portfolio, Aura3D, MZ, Print, NotFound가 페이지 단위로 명확히 구분되어 있다.
- 프로젝트 공통 정보가 src/content/projects.ts에 모여 있어 목록과 상세의 핵심 정보가 비교적 일관된다.
- TypeScript strict 설정, noUnusedLocals/noUnusedParameters, ESLint의 no-explicit-any 규칙이 적용되어 있다.
- HashRouter와 상대 base 경로를 사용하여 GitHub Pages 정적 호스팅 제약에 대응하고 있다.
- 본문 건너뛰기, focus-visible, 대체 텍스트, prefers-reduced-motion, 의미 있는 heading 구조 등 기본 접근성을 고려했다.
- 반응형 레이아웃과 별도 인쇄 스타일, 이미지 로딩 대기 후 전체 PDF 출력 기능이 구현되어 있다.
- GitHub Actions가 npm ci, lint, build, Pages 업로드·배포를 수행한다.

검증 결과
- npm run lint: 통과
- npm run build: 통과
- 프로덕션 산출물: JS 약 272.11 kB( gzip 84.44 kB), CSS 약 34.52 kB(gzip 6.74 kB)
- 최초 샌드박스 실행에서는 상위 디렉터리 접근 제한으로 Vite 설정 로딩이 실패했으나, 권한 제약 밖에서 동일 명령을 실행하자 정상 통과했다. 코드 빌드 오류는 아니다.

3. 수정이 필요한 부분

[P0: 배포 또는 핵심 사용을 막는 문제]
- 현재 확인된 P0 코드 오류는 없다. build와 lint가 모두 통과하고 GitHub Pages 워크플로도 존재한다.

[P1: 우선 개선 권장]

3-1. 이미지 용량과 초기 표시 성능
- 일부 이미지가 크다: aura3d-architecture.png 약 1.33 MB, mz-search-map.png 약 1.22 MB, aura3d-erd.png 약 0.88 MB, aura3d-dashboard.png 약 0.76 MB.
- 목록 및 상세의 첫 이미지에는 명시적 width/height가 없어 이미지 로드 전후 레이아웃 이동 가능성이 있다.
- 제안: 원본을 보존하면서 WebP 또는 AVIF 파생본을 만들고 picture/srcset으로 화면 크기별 파일을 제공한다. 표시 크기에 맞는 width/height 또는 aspect-ratio도 지정한다.
- 기대 효과: 첫 화면 전송량과 LCP, 레이아웃 안정성 개선. 실제 개선 수치는 Lighthouse 전후 측정 후에만 기록한다.

3-2. 콘텐츠 근거와 링크 강화
- 포트폴리오의 강점은 기술 서술이 구체적이라는 점이지만, 각 프로젝트 상세에서 코드 저장소·README·커밋·테스트 결과로 바로 이동할 수 없다.
- “호출량 약 90% 감소”는 반복 노출되므로 측정 조건(호출 주기, 비교 횟수, 상태 변화 횟수, 계산식)과 캡처 또는 테스트 기록을 함께 제공해야 신뢰도가 높아진다.
- 제안: projects 데이터에 확인된 링크만 선택적으로 추가하고, 상세 페이지에 ‘근거 자료’ 영역을 만든다. 비공개이거나 확인할 자료가 없으면 링크를 억지로 만들지 말고 현재 설명을 유지한다.
- 주의: 검증되지 않은 성과, 기여도, 사용자 수, 성능 수치는 추가하지 않는다.

3-3. 페이지별 메타데이터와 공유 품질
- index.html의 title과 description이 모든 HashRouter 화면에 동일하게 적용된다.
- Open Graph 이미지·제목, canonical, 구조화 데이터, favicon·manifest가 확인되지 않는다.
- 제안: 라우트별 document.title과 meta description을 갱신하는 작은 공통 컴포넌트를 추가하고, 검증된 소개 정보만으로 Person/CreativeWork JSON-LD와 기본 OG 메타데이터를 구성한다.
- HashRouter의 해시 URL은 정적 배포에는 안전하지만 검색엔진별 색인·공유 URL 표현에는 제약이 있다. GitHub Pages 유지가 우선이면 HashRouter를 유지하고 메타데이터 개선부터 적용한다.

3-4. 자동 회귀 검증 부재
- 현재 lint와 TypeScript 빌드는 정적 오류를 잘 잡지만, 라우팅·모바일 메뉴·챕터 이동·전체 PDF 이미지 대기 같은 동작을 검증하는 테스트가 없다.
- 제안: Vitest와 Testing Library로 공통 컴포넌트 및 라우트 렌더링을 최소 검증하고, Playwright로 주요 페이지 접근·내부 링크·모바일 메뉴·인쇄 페이지 렌더링을 한 개의 핵심 시나리오로 확인한다.
- GitHub Actions에는 test 단계를 build 전에 추가한다. 테스트 도입 전에는 워크플로 범위를 불필요하게 늘리지 않는다.

[P2: 유지보수성과 완성도 개선]

3-5. 중복 상세 페이지 구조
- Aura3D와 MZ에서 상세 Hero, 요약 정보, 수치 영역, ChapterHeading이 반복된다.
- 프로젝트가 두 개인 현재는 이해하기 쉽지만, 사례가 늘면 마크업과 접근성 수정이 여러 파일에 중복된다.
- 제안: 당장은 ChapterHeading만 공통화하고, 세 번째 프로젝트가 실제로 추가될 때 DetailHero와 공통 섹션 구조를 추출한다. 과도한 범용 스키마화는 피한다.

3-6. 사용되지 않는 컴포넌트
- EvidencePlaceholder.tsx는 현재 어느 페이지에서도 import되지 않는다.
- 제안: 앞으로 빈 증거 영역을 실제로 표시할 계획이 없다면 제거한다. 사용 목적이 있다면 대상 페이지와 표시 조건을 먼저 정의한다.

3-7. 프로젝트 데이터 접근의 안전성
- Aura3D와 MZ가 각각 projects[0], projects[1]에 의존한다. 배열 순서를 바꾸면 상세 페이지의 내용이 뒤바뀔 수 있다.
- 제안: id 기반 조회 함수 또는 id를 키로 하는 객체를 사용한다. 찾지 못한 경우를 TypeScript에서 명시적으로 처리한다.

3-8. 모바일 메뉴 사용성
- Escape 닫기와 포커스 복귀는 구현되어 있으나, 메뉴 외부 클릭 닫기와 열린 상태에서의 명확한 포커스 흐름은 제공하지 않는다.
- 제안: 작은 화면에서 외부 클릭 또는 메뉴 링크 선택 시 명시적으로 닫고, 필요하면 첫 메뉴 항목으로 포커스를 이동한다. 키보드와 스크린리더로 실제 동작을 확인한다.

3-9. 전체 PDF 문서의 중복 ID
- Print 페이지는 Home, Resume, Portfolio와 두 상세 페이지를 한 DOM에 합친다. 현재 각 구성 요소의 ID는 대체로 다르지만, 컴포넌트 재사용이나 향후 섹션 추가 시 중복 ID가 발생하기 쉬운 구조다.
- 내부 링크도 일반 페이지 라우팅을 그대로 유지해 PDF 문서 내 탐색 링크처럼 동작하지 않는다.
- 제안: printMode 또는 idPrefix를 전달해 인쇄 전용 ID와 링크 동작을 분리한다. Playwright 또는 브라우저 PDF 미리보기로 페이지 잘림, 빈 페이지, 중복 ID를 검사한다.

3-10. 도구 버전과 유지보수 정책
- package.json은 caret 범위를 사용하므로 설치 시 호환 가능한 최신 부버전으로 이동할 수 있다. 실제 빌드에서는 Vite 7.3.6이 사용됐다.
- 제안: package-lock.json을 기준으로 재현성을 유지하고 Dependabot 또는 정기 점검을 도입한다. React, Vite, ESLint, typescript-eslint을 한 번에 무리하게 올리지 말고 build·lint·test를 통과하는 단위로 갱신한다.

3-11. 문서 정보 동기화
- 연도, 재직 상태, 경력 기간, 프로젝트 기간, 기술 버전이 여러 페이지와 README에 분산되어 있다.
- 제안: 개인·경력·교육 정보도 콘텐츠 파일로 분리하는 방안을 검토한다. 다만 변경 빈도가 낮다면 우선 projects 데이터의 링크와 근거 필드 확장만 적용하고 대규모 CMS 구조는 만들지 않는다.

4. 추가 기능 브레인스토밍

[가치가 높고 정적 사이트에 잘 맞는 기능]

4-1. 프로젝트 근거 패널
- 프로젝트별 GitHub, 설계 문서, 테스트 기록, 배포 화면 등 실제 확인 가능한 자료를 한곳에 제공한다.
- 채용 담당자가 서술과 증거를 빠르게 연결할 수 있어 가장 먼저 추천한다.

4-2. 기술·역할 필터
- 프로젝트가 세 개 이상이 될 때 Java, Spring, Data, AI, Infra 및 개인/팀 역할로 사례를 좁힌다.
- 현재 두 개뿐이므로 지금 구현하면 UI 복잡도만 늘 수 있다. 프로젝트 증가 시점에 도입한다.

4-3. 설계 결정 기록(Decision Log)
- 각 사례에 ‘문제 / 선택지 / 선택 / 이유 / 한계 / 다음 개선’을 짧게 추가한다.
- 새 성과를 주장하지 않고도 사고 과정과 트레이드오프를 보여줄 수 있다.

4-4. 검증 가능한 데모 미디어
- 실제 서비스 연결 대신 짧은 무음 영상, GIF 또는 단계별 스크린샷으로 핵심 흐름을 보여준다.
- 정적 사이트 원칙을 유지하며 외부 서비스 중단의 영향을 피할 수 있다. 개인정보·API 키·고객사 화면은 반드시 제거한다.

4-5. 인쇄 범위 선택
- 전체 PDF 외에 이력서만, 프로젝트 한 개만 저장하는 현재 기능을 더 명확한 메뉴로 제공한다.
- 인쇄 버튼에 페이지 수 예상 또는 포함 항목 안내를 제공하면 사용자가 결과를 예측하기 쉽다.

4-6. 접근성·품질 상태 페이지
- Lighthouse, 접근성 점검, 테스트 통과 여부를 README 배지나 짧은 품질 섹션으로 공개한다.
- 점수는 측정 환경과 날짜를 함께 기록하고 자동 검증 결과가 있을 때만 표시한다.

4-7. 한국어/영어 전환
- 해외 지원이 실제 목표일 때만 콘텐츠 번역을 정적 데이터로 제공한다.
- 단순 기계 번역 대신 프로젝트 역할과 기술 용어를 검수할 수 있을 때 도입한다. 현재 우선순위는 낮다.

4-8. 변경 이력
- 프로젝트 설명, 근거 자료, 이력서 갱신일을 간단히 표시한다.
- 정보의 최신성을 보여주되 실제 커밋 또는 수정일에 근거해 자동 또는 수동 관리한다.

[현재는 권장하지 않는 기능]
- 문의 폼 백엔드, 자체 분석 서버, 데이터베이스, 서버리스 함수: 현재 정적 배포 원칙과 작업 지침을 벗어난다. 연락은 mailto와 GitHub 링크로 충분하다.
- 방문자 수·좋아요·댓글: 채용 포트폴리오의 핵심 가치와 거리가 있고 개인정보·운영 부담이 생긴다.
- 근거 없는 기술 숙련도 퍼센트나 별점: 비교 기준이 불명확해 신뢰도를 낮출 수 있다.
- 프로젝트가 두 개인 상태의 복잡한 검색, 태그 시스템, CMS: 유지보수 비용 대비 효용이 작다.

5. 권장 실행 순서

1단계: 신뢰도와 성능(높은 우선순위)
- 대용량 이미지 최적화 및 크기 명시
- 확인 가능한 프로젝트 링크·측정 조건·근거 자료 추가
- 라우트별 title과 description 추가
- 사용되지 않는 EvidencePlaceholder 정리

2단계: 회귀 방지와 사용성
- id 기반 프로젝트 조회로 전환
- 모바일 메뉴 상호작용 보강
- 핵심 컴포넌트 테스트와 주요 라우트 E2E 테스트 추가
- 전체 PDF의 ID·링크·페이지 분할 검증

3단계: 콘텐츠 확장
- 설계 결정 기록과 한계·다음 개선 섹션 추가
- 검증 가능한 데모 미디어 제공
- 프로젝트가 세 개 이상일 때 필터 도입
- 실제 지원 대상이 있을 때 영어 버전 검토

6. 제안하는 완료 기준

- npm run lint와 npm run build가 로컬 및 GitHub Actions에서 모두 통과한다.
- 주요 이미지의 포맷·크기 변경 전후를 측정하고, 화면 품질 저하와 깨진 경로가 없다.
- 홈, 이력서, 포트폴리오, 두 상세 페이지, 404, 전체 PDF를 데스크톱과 모바일에서 확인한다.
- 키보드만으로 메뉴, 프로젝트 링크, 챕터 이동, 인쇄 버튼을 사용할 수 있다.
- 추가한 성과·기여·링크는 저장소나 문서 등 확인 가능한 근거를 가진다.
- GitHub Pages 배포 후 새로고침, 해시 라우팅, 이미지와 PDF 출력이 정상 동작한다.

7. 결론

현재 코드는 작은 정적 포트폴리오에 적합한 단순한 구조를 유지하며 build와 lint도 통과한다. 다음 개선의 중심은 기능 수를 늘리는 것보다 ‘근거로 연결되는 기술 서술’, ‘이미지 전송 최적화’, ‘라우트별 공유 정보’, ‘핵심 동작의 자동 검증’이어야 한다. 가장 효과적인 첫 작업은 대용량 이미지 최적화와 프로젝트별 근거 패널이며, 복잡한 필터나 CMS는 실제 프로젝트 수가 늘어난 뒤 도입하는 편이 합리적이다.
